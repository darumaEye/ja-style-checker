# 公用文要領ベース校閲スキル

社内文書の日本語表記を、文化審議会国語分科会「新しい『公用文作成の要領』に向けて」（令和3年3月12日）の考え方に基づいてチェックする。国の府省庁向けの原文ルールをそのまま適用するのではなく、社内文書（大半は要領でいう「解説・広報等」に近い性格）向けに柔軟モードを既定とする。

要領のルールに加えて、社内独自の校閲ルールを追加で適用できる。また、Claude Projectのプロジェクト知識に案件ルール・個人ルールが置かれていれば、それも合わせて適用する。詳細は「案件ルール・個人ルールの追加方法」「ルール間の優先関係」を参照。

## ファイル構成

このスキルが実行時に参照するファイルは以下の4つ。

| ファイル | 種類 | 役割 |
|---|---|---|
| `SKILL.md`（このファイル） | 手順書 | 校閲の進め方・出力フォーマットを定義する |
| `references/koyobun_rules.generated.md` | ルールファイル | 公用文要領ルールのうち、AI判断層が参照する指針 |
| `references/company_rules.generated.md` | ルールファイル | 社内独自ルールのうち、AI判断層が参照する指針 |
| `scripts/mechanical_check.py` | スクリプト | 機械判定層を実行するPythonスクリプト |

案件ルール・個人ルールはこのスキルには同梱しない（詳細は後述）。

## 校閲は2層構成で行う

要領ルールには、機械的に一意に判定できるものと、文脈判断が必要なものが混在している。この2つを混同すると指摘の再現性が下がり、解釈違いの原因になる。したがって、必ず分けて処理する。

1. 機械判定層 — `scripts/mechanical_check.py` を実行する。表記ゆれ・常用漢字表外・数字表記・句読点統一など、ルールが一意に定まる項目を正規表現・辞書ベースで検出する。実行結果はJSONで返される。
2. AI判断層 — Claude自身が `references/koyobun_rules.generated.md`（要領ルールの判断区分）、`references/company_rules.generated.md`（社内独自ルール）を踏まえて判断する。加えて、現在の会話がClaude Projectで行われており、そのプロジェクト知識に`project_rules.md`（案件ルール）・`user_rules.md`（個人ルール）があれば、それも判断材料に含める。専門用語の説明要否、文体の親しみやすさ、一文の論点整理などが該当する。

## 実行手順

1. 対象資料を読み込む。
   - `.md` はそのままテキストとして読む。
   - `.pptx` は pptx スキルの手順でテキスト（本文・スピーカーノート）を抽出する。
   - `.docx` は docx スキルの手順で本文を抽出する。
2. 抽出した本文をプレーンテキストとして一時ファイルに保存し、`scripts/mechanical_check.py <ファイル>` を実行する。
3. スクリプトが返したJSON結果（該当箇所・ルールID・レベル・修正案）を確認する。
4. `references/koyobun_rules.generated.md`・`references/company_rules.generated.md`（および、プロジェクト知識にあれば`project_rules.md`・`user_rules.md`）の「判断」区分の各項目について、本文を通読しながらClaude自身が該当箇所を洗い出す。機械判定層で拾えなかった「及び／並びに」の対応関係、専門用語の説明要否、文体の親しみやすさなどはここで扱う。
5. 機械判定層・AI判断層の指摘を統合し、レベル別（要修正／注意／参考）に並べ替える。同じ箇所への重複指摘はまとめる。
6. 出力する。フォーマットは以下を基本とする。

```
## 校閲結果（◯件）

実施日時：YYYY-MM-DD HH:MM

### 要修正（法令・公用文の原則に明確に反する）
| 該当箇所 | 修正案 | 指摘理由 |
|---|---|---|

### 注意（社内文書として統一・検討が望ましい）
| 該当箇所 | 修正案 | 指摘理由 |
|---|---|---|

### 参考（好みや文脈次第で採否を検討）
| 該当箇所 | 修正案 | 指摘理由 |
|---|---|---|

一言講評：（文書全体の傾向を2〜3文で）
```

実施日時は現在の日付・時刻を記載する（時刻が分からない場合は日付のみでよい）。校閲履歴をファイルに保存する際の目印として使う想定。

このスキル自体は校閲結果をファイルに保存しない（チャットへの表示が既定）。ユーザーが「ファイルに保存して」等と出力方法を指定した場合は、同じフォーマットの内容をその指示に従って出力する。

7. 「要修正」の件数が多い、または大幅に本文を書き換えた場合は、再チェックを勧める一文を末尾に添える。

## モードの切り替え

既定は柔軟モード（解説・広報等向け）。社内文書は法令ではないため、要領が「解説・広報等」に認めている表記の緩和（振り仮名の活用、送り仮名を省略しない書き方等）を許容する。

ユーザーが「告示・通知並みに厳格にチェックして」等と明示した場合のみ厳格モードに切り替え、`references/koyobun_rules.generated.md` の「厳格モードのみ」の項目も適用する。

## 案件ルール・個人ルールの追加方法

案件独自ルール・個人ルールは、社内ルールや要領ルールと違ってこのスキル自体には同梱されていない。追加したい場合は、ユーザーが以下の手順で用意する（Claudeが行う作業ではない）。

1. Claude Projectを作成する（案件ごとに1つが目安）。
2. そのプロジェクトの「プロジェクト知識」に、`project_rules.md`（案件ルール）・`user_rules.md`（個人ルール）を追加する。書式は`company_rules.md`と同様の表形式（ルール／レベル／理由）を推奨する。

この会話がそのProjectの中で行われていれば、AI判断層は自動的にこれらのファイルを参照する。Project化していない単発の会話では、案件ルール・個人ルールなしで校閲する。

## ルール間の優先関係

要領ルール・社内ルール・個人ルール・案件ルールが矛盾する場合は、より個別的なルールを優先する。優先順位は次のとおり（下にいくほど優先度が高い）。

1. 公用文要領ルール（`koyobun_rules.generated.md`）
2. 社内独自ルール（`company_rules.generated.md`）
3. 個人ルール（`user_rules.md`）
4. 案件独自ルール（`project_rules.md`）

個人ルールより案件ルールを優先するのは、特定の案件・クライアントの要求は、担当者個人の好みより優先されるべきという考え方による。

矛盾するルールを適用した場合は、その旨を指摘理由に明記する（例：「要領ではA、社内ルールではBのため、Bを推奨」「社内ルールではB、本案件のルールではCのため、Cを推奨」）。要領ルール・社内ルールの編集・追記の手順は`README.md`を参照（Claudeが行う作業ではない）。

## 指摘を書く際の注意

- 指摘理由は平易な説明を先に書き、要領のどの章・項目に基づくかは末尾に（）で簡潔に添える（例：「数字は3桁ごとにコンマ区切りにする原則があります（Ⅰ-4-イ）。」）。
- 修正案は本文にそのまま反映できる形で示す。
- 誤検出を避けるため、固有名詞・引用部分・コードやURLなどは対象外とする。
- 「参考」レベルの指摘は強制ではないことが伝わる書き方にする（「〜という選択肢もあります」等）。
